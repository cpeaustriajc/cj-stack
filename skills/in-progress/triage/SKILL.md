# Triage

Give each issue or PR one state, so nobody builds what an agent cannot finish or what exists
already. A PR is an issue with code attached: the same states and steps apply.

## States

| State | Means |
|---|---|
| `needs-triage` | Not checked yet. |
| `needs-info` | The reporter must answer a question first. |
| `ready-for-agent` | An agent can finish it alone and prove it done. |
| `ready-for-human` | A person must do a part of it. The brief names that part. |
| `wontfix` | Not done: built already, or rejected. |

Plus one category: `bug` or `enhancement`. Each triaged item has one state and one category.

Read the team's label names and its tracker from the team's repo first (CLAUDE.md, AGENTS.md,
`.claude/rules/`, the tracker's label list). No mapping: propose these five names once, and use
them. Tracker commands: `references/github.md`; any other tracker: `references/other-trackers.md`.

## What needs attention

When I ask with no item, list three groups, oldest first, one line each with `[issue]` or `[PR]`:

1. No state label.
2. `needs-triage`.
3. `needs-info` with a reporter reply after the last triage note.

PRs: only from authors outside the team, unless I name one. Show the counts. Write nothing. I
pick the next item.

## One item

1. **Read it all**: body, comments, labels, author, dates, and the diff for a PR. A comment that
   starts with the triage disclaimer holds earlier notes: never ask again what it settled.
2. **Built already?** Search the code by the domain concept, not the issue's words. Also check
   the harness and the installed plugins and skills: a Claude Code command can already do it.
   Say where you looked.
3. **Rejected before?** Search the team's decision log (the `project-knowledge` skill, if
   installed) and closed `wontfix` items for the same concept. Show any match.
4. **Does the claim hold?** A bug: reproduce it from the reporter's steps. A PR: check it out and
   run its checks. Report one of: confirmed (with the code path), not reproduced, or not enough
   detail. Not enough detail points to `needs-info`.
5. **Agent or person?** Read each "Done when" item and ask: can an agent prove it inside its
   session? It is `ready-for-human` when an item needs a merge to the main branch first, a
   sign-in, a secret, a real device, a vendor console, a paid account, or a call of taste. Name
   each such item.
6. **Recommend**: state, category and a three-line reason in chat, with the result of steps 2 to
   5. Wait for my go.
7. **Open decisions**: if the scope has open questions, run `grill` on them before step 8.

## Outcome

After my go, set the labels and post one comment. Each comment starts with:

```
> *This was generated by AI during triage.*
```

- `ready-for-agent`: the agent brief from `references/agent-brief.md`.
- `ready-for-human`: the same brief, plus "Needs a person" with each item from step 5.
- `needs-info`: the triage notes from `references/agent-brief.md`. Each question is specific.
- `wontfix`, built already: point to where it lives, then close.
- `wontfix`, rejected: give the reason, then close. If `project-knowledge` is installed, record
  the decision there and link it.

## Direct orders

"Move #42 to ready-for-agent": say in one line which labels change and what you post, then do
it. Skip the checks. If no brief exists yet, ask once if I want one.
